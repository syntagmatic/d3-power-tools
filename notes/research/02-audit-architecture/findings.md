# Findings — Audit Data Layer Architectural Review

This document reviews the project's current audit and iteration code to surface the structural gaps that prevent dossier graduation criteria from being machine-checkable. It is not a literature review.

## Method

Read end-to-end:
- `scripts/run-audit-pipeline.py` (490 LOC) — the audit pipeline writing `evals/runs/*.json`.
- `scripts/iterate-block.py` (409), `iterate-prompt.py` (501), `iterate_lib.py` (903) — the autoresearch loop.
- `scripts/eval-hierarchy-bundles.py` (969) — the transition evaluator for one specific block.
- `scripts/staging.py` (230) — pure utility for skill staging and stream-json parsing.
- `scripts/generate-blocks-claude.py` / `generate-blocks-gemini.py` — generation harnesses.
- `evals/iterations/index.html:88-300` — the JavaScript that consumes audit JSON.

Cross-checked git history on the canonical weight tuple (`scripts/run-audit-pipeline.py:40`).

## Findings

### F1. The composite formula is duplicated three ways and disagrees with itself

Three call sites compute composite from per-dimension scores:

- `scripts/run-audit-pipeline.py:266-269` writes `composite = None` when any dimension is missing.
- `scripts/iterate-block.py:84-90` reads the pipeline's output, **overwrites the null** with a renormalized weighted average over present dimensions.
- `scripts/iterate-prompt.py:91-97` is line-for-line identical to the iterate-block block.

The two policies — "incomplete = no composite" and "incomplete = best-effort composite" — coexist silently. The pipeline writes one value; the iterate scripts overwrite it before logging. The on-disk record in `evals/iterations/*.json` reflects the iterate scripts' renormalized value, not the pipeline's null.

The JS reader at `evals/iterations/index.html:291` does `d.composite_after ?? d.scores?.composite` — null is treated as a fallthrough, never as a signal. **Nothing downstream interprets null as "this run is incomplete."** The pipeline's null-policy is dormant code masking a buggy interaction.

Git history shows the weight tuple `(0.30, 0.25, 0.25, 0.20)` has changed exactly once — a rename in `570c9ea` (`polish→visual_critic` etc.), not a re-weighting. So the duplication is unlikely to *cause* a bug from value drift; it's friction-on-reading and a trap for future changes.

### F2. The dimension list is a folk schema across four consumers

The tuple `("visual_critic", "encoding_integrity", "stress_test", "cognitive_load")` appears hardcoded in:

- `scripts/run-audit-pipeline.py:33` (canonical) — `TOOLS = {...}`
- `scripts/iterate-block.py:98` (re-iterated for prompt notes) — 4-tuple
- `scripts/iterate-prompt.py:149` — **5-tuple**, including `transition`, to support hierarchy-bundles
- `evals/iterations/index.html:796-821` (JS, in tooltip rendering) — 4-tuple

The dimension set is implicit: you discover it by reading any one of the four. Adding a fifth dimension touches all four. Renaming a dimension touches all four plus the rendered HTML. The keys `{dim}_note` and the special-case top-level `flags` extend the implicit schema without naming it anywhere.

### F3. The transition evaluator runs on a parallel track that never converges

`scripts/eval-hierarchy-bundles.py` is invoked for `block_id == "hierarchy-bundles"` only:

- It is dispatched by `scripts/iterate-prompt.py:49-50` via a hardcoded `if`. The branch is not present in `iterate-block.py`.
- It writes results to `evals/experiments/hierarchy-bundles-runs.json`, a file the audit pipeline never reads.
- It computes composite as `0.6 * t_score + 0.4 * vc` inline at line 843. There is no `WEIGHTS` dict; the literals are not named.
- Its dimensions are `transition` + `visual_critic`. The general pipeline's dimensions are `visual_critic + encoding_integrity + cognitive_load + stress_test`. **Both schemas share `visual_critic` (same meaning) but produce composites on different scales.**

A future block whose `block_id` changes from `hierarchy-bundles` to anything else would silently start going through the general pipeline, producing a composite on a different scale, with no error or warning. The seam between general and transition evaluation is real but invisible.

### F4. Provenance is at run-level, not result-level

`scripts/run-audit-pipeline.py:273-281` writes a `run_data` dict with `timestamp`, `git_sha`, `skill_shas`, `block_set`, `model`, `cli_version`. These are run-wide.

The dossier 01 graduation criterion ("cross-model audit composites within ±0.5 of baseline") implies per-result provenance: the same block can be audited by Sonnet and Opus in the same run, or generated by Gemini and judged by Claude. The current shape can't represent that — `model` is one field per run.

`evals/anchors.json` records calibration drift across runs but doesn't preserve generator/judge separation either. The flat `run_data["model"]` is the only model record, and the audit pipeline conflates "the model that ran the inspection skills" with "any other model context."

### F5. There is no `compare()` primitive

The graduation criterion "within ±0.5 of baseline" is a comparison between two runs. The only code today that compares anything is the iterate scripts' `decide_block` and `decide_redesign` functions in `iterate-block.py` and `decide_prompt` / `decide_prompt_quality` in `iterate-prompt.py`. They:

- Take per-iteration scores plus a baseline scores dict.
- Return a string verdict (`"keep"` / `"discard"`) plus a description string for logging.
- Are bespoke per script — block iterate uses LOC delta, prompt iterate uses time delta, both touch composite in different ways.

A future dossier needs a *structured* comparison: schema match, per-dimension diff, composite diff, flag-set change, render-error count. None of that exists today.

### F6. iterate-block and iterate-prompt are 95% the same loop, drifted

Both implement: baseline → propose → audit → decide → log → check convergence → repeat. Differences:

- State: iterate-block uses git worktrees + commits; iterate-prompt uses a file holding the current prompt.
- Metric: iterate-block tracks LOC; iterate-prompt tracks generation time.
- Decision string format: `-{Δlines} lines` vs `-{Δseconds:.0f}s`.
- History line format: implicit, format-coupled to a `{history}` placeholder in the proposer template.
- Hierarchy-bundles routing: iterate-prompt has it, iterate-block doesn't.

The shared loop has no module. `iterate_lib.py` is the parts bin (worktree helpers, TSV append, JSON write, progress-HTML generation), but it does not own the loop control flow. Patches landing in one script don't propagate to the other.

This is dossier-relevant because **a research-oriented project's primary loop is per-dossier comparison, not per-block iteration**. The autoresearch loops may not even survive the pivot. If they do, they should be one loop, parameterized.

### F7. The discriminator is acknowledged-overfit and not used as a gate

`evals/discriminator.json` is a Ridge regression at CV R² ≈ -0.33 — severely overfit. `notes/CRITIQUE.md` documents this. Dossier 01's critique prompt (Q3) asks whether the merge proposal reduces the conflation driving that signal, but no graduation gate depends on the discriminator. It exists as evidence and no more.

This is not a defect; it's a soft state. Dossier 02 inherits the question of whether to revive, retire, or sanity-check. The default in this dossier is **archived, not a gate**.

### F8. The eval artifacts are referenced by dossier 02 itself

`PROMPT.md` (this dossier, prior version) listed `evals/anchors.json`, `evals/discriminator.json`, `notes/V2-FINDINGS.md`, `notes/AUTORESEARCH.md`, `notes/CRITIQUE.md` as inputs. If the v1 archive moves these files to `archive/v1/evals/` before this dossier's synthesis runs, the synthesis's own input list breaks. Sequencing matters: archive **after** synthesis consumes them, or update PROMPT.md paths concurrently.

## Implications for the architecture

The deepest concept this review surfaced is **the audit result**: what produces it, what its schema is, and how two of them are compared. That's the load-bearing module the new package must define cleanly. Everything else (evaluator dispatch, run aggregation, comparison primitives) is downstream of it.

The second concept is **provenance discipline**. Without per-result provenance, adversarial pairing cannot be enforced and cross-model comparison cannot be done. The data class must carry it.

The third is **schema-as-data**, not schema-as-implicit-contract. Two evaluator schemas exist in the project today (general, transition); both currently exist as folk knowledge. They should be named, declared, and referenced.

## What this review cannot say

- Whether the new schema should be a Python dataclass or a TypedDict or a Pydantic model. That's the synthesizer's call.
- Whether `Evaluator` is a Protocol, an ABC, or just a callable signature. Synthesizer's call.
- What the JSON shape *should* look like in detail. Examples will be fastest to argue about in `synthesis.md`.
- Whether `iterate-block.py` should be rebuilt or archived for now. Depends on whether per-block iteration survives the research pivot — a dossier-level question, not an architecture question.

## Pre-registered facts that the synthesis will not relitigate

- The composite tuple is `(0.30, 0.25, 0.25, 0.20)` for the four general dimensions, stable across history. The new code uses these unless the synthesis explicitly proposes otherwise.
- `visual_critic` is shared between general and transition schemas with the same meaning. Comparison across schemas is allowed *only* on shared dimensions; composites are not cross-schema comparable.
- The on-disk JSON shape is allowed to change — there is no live consumer that requires backward compatibility once `evals/iterations/index.html` is regenerated from the new format.
- The discriminator is archived by default. Synthesis may resurrect it only with a concrete role.
